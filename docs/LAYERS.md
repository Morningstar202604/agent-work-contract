# 分层模型：每一层放什么，怎么判断放错了

规则体系分七层。判断标准只有一条：**这层是「何时生效」决定的，不是内容决定的。**

## 七层职责

| 层 | 生效时机 | 放什么 | 不该放什么 |
|---|---|---|---|
| **配置** `cli/config.json` | 进程启动时读一次 | 预算、并发、超时、开关、路径 | 任何行为逻辑 |
| **规则** `AGENTS.md` | 每轮常驻 | 判定条件、优先级裁决、底线、指针 | 完整操作流程、代码、模板 |
| **提示词** `hooks/lib/polish.js` `recall.js` | 每轮注入 | 一句话提醒 + 指针 | 规则正文、模板全文 |
| **钩子** `hooks/*.js` | 事件触发时 | 确定性门禁、状态记录、注入 | 需要判断力的业务逻辑 |
| **技能** `skills/*/SKILL.md` | 命中触发词后读全文 | 完整流程、模板、清单、示例 | 全局底线（应在规则层） |
| **子代理** `agents/*.md` | 显式调用 | 独立上下文的专业化执行 | 需要与主线程共享状态的工作 |
| **命令** `commands/*.md` | 手动 `/` 触发 | 固定序列的一次性动作 | 需要按情况分支的流程 |

## 判定顺序（放错层时按此迁移）

```
这件事必须「每次」发生吗？
├─ 是 → 能机器判定吗？
│        ├─ 能 → 钩子（确定性门禁）
│        └─ 不能 → 规则（AGENTS.md 常驻一句）+ 技能（细节）
└─ 否 → 只在特定任务发生吗？
         ├─ 是 → 技能
         └─ 否（只在启动时） → 配置
```

## 典型错位与正确归属

| 错位现象 | 问题 | 正确做法 |
|---|---|---|
| 规则里写完整命令清单 | 每轮常驻白耗上下文 | 规则留一句「见技能 X」，细节下沉技能 |
| 技能里写「永远不要删除生产数据」 | 只在命中该技能时生效，等于没有 | 上升到规则层底线 |
| 提示词里重复规则全文 | 每轮多出上千 token | 提示词只留一句提醒 + 指针 |
| 钩子里判断「这个需求是否合理」 | 钩子不该有判断力 | 交给技能/模型，钩子只做确定性判定 |
| 配置里写业务规则 | 改规则要重启进程 | 移入规则或技能 |
| 两个技能讲同一件事 | 触发词互相抢，命中不稳 | 合并，保留一个主技能 + 一个指针 |

## 上下文预算账

| 层 | 常驻成本 | 预算 |
|---|---|---|
| AGENTS.md | ~19 KB（每轮前缀） | 无硬上限，但应控制在 20 KB 内 |
| 技能描述 | 96 × ~170 字符 ≈ 16.6 KB | 60,000 字符（`skills.metadataBudget`） |
| 提示词注入 | 每轮 ~600 字符 | 越低越好 |
| 记忆注入 | 每轮 3–5 行 | 标题索引只在回顾时给 |

**核心权衡**：常驻的东西贵，按需的东西便宜。所以「必须每次生效」才放常驻层，其余全部下沉。

## 迁移检查清单

改任何一层前先问：

1. 这条规则真的需要**每轮**生效吗？
2. 它能否被**一条命令**判定？能就做钩子。
3. 它已经在**别的层**存在了吗？（grep 一下再动手）
4. 搬走之后，**约束力**会下降吗？会就别搬，或降到只搬细节。
5. 搬完**回归测试**过了吗？（selftest + verify）

## 层的稳定性

| 层 | 变更成本 | 变更频率 |
|---|---|---|
| 配置 | 需重启 | 低 |
| 规则 | 影响每轮，需全量回归 | 低 |
| 提示词 | 影响每轮，需 selftest | 中 |
| 钩子 | 需 selftest 覆盖 | 中 |
| 技能 | 需 verify + 描述长度检查 | 高 |
| 子代理 | 需 verify 计数 | 中 |
| 命令 | 独立，风险最低 | 低 |

越靠上越稳定，越靠下越灵活。**把易变的东西放上层是设计错误**——每次改动都要全量回归。

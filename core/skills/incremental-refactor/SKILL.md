# 增量重构

## 铁律

1. **行为不变**：重构不改变外部可观察行为；要改行为就是改需求，单独做。
2. **测试先行**：没有测试覆盖的地方，先补特征测试（characterization test）再动。
3. **小步提交**：每个可编译、可测试的状态都是一个提交。
4. **随时可停**：任何一步中断，仓库都应处于可用状态。

## 流程

```
1. 锁定范围：要改哪个模块，边界在哪
2. 补测试：覆盖现有行为（不求完美，求能发现回归）
3. 跑绿：确认基线通过
4. 小步改：一次一个手法（提取函数 / 内联 / 改名 / 移动）
5. 每步验证：跑测试
6. 清理：删掉临时兼容层
7. 提交：一个手法一个提交，或一个连贯小目标一个提交
```

## 常见手法

| 目标 | 手法 |
|---|---|
| 函数太长 | 提取函数（Extract Function） |
| 参数太多 | 引入参数对象 |
| 重复代码 | 提取公共函数，但别过度抽象 |
| 深层嵌套 | 卫语句提前返回 |
| 类职责过多 | 按变化原因拆分 |
| 替换实现 | 保留接口，换内部实现，测试护航 |

## 不要做

- 一次重构跨多个模块。
- 重构同时改需求。
- 没有测试就大改。
- 为了「架构更优雅」重写能跑的代码。
- 留下半成品兼容层。

## 何时停止

- 达到本次目标即停，不顺手扩大范围。
- 发现更大的问题：记录到记忆文件「待办与阻塞」，不在本轮解决。

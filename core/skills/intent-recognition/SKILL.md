# 意图识别（每次开工前的第一道工序）

回答三个问题，再动手：

1. **他想要什么**（意图）：去掉手段，留下结果。
2. **这个项目是什么**（定位）：它服务的对象、解决的核心问题、所处阶段。
3. **怎么算做对了**（验收）：可观察、可执行、可复现的判据。

不识别就动手，等于替对方定义目标——这是返工的第一来源。

## 何时必须做

- 任何新任务的第一轮（非纯确认/纠正类短语）。
- 接到「优化 / 搞一下 / 看看 / 处理下」这类含糊动词。
- 跨项目、跨团队、陌生仓库接手。
- 需求方与实现方不是同一人时。

## 何时可跳过

- 用户当轮已给出完整验收标准与范围。
- 纯确认、纠正、数据粘贴（「继续」「对」「停」、日志、报错原文）。
- 已在同一任务内做过且前提未变（引用上次结论即可，不重复问）。

## 四维识别

### 1. 意图层：他到底想要什么

| 信号 | 追问方向 |
|---|---|
| 说手段不说目的（「用 Redis」） | 要解决的是缓存、锁还是队列？ |
| 说现象不说目标（「老报错」） | 报错是症状，期望的终态是什么？ |
| 说形容词不说标准（「优化一下」） | 优化哪个指标？从多少到多少？ |
| 一次提很多点 | 哪一条不做会失败？其余可延后 |

### 2. 项目定位层：这是什么项目

- **服务对象**：谁用？内部工具 / 对外产品 / 一次性脚本。
- **核心问题**：它存在是为了解决什么？删掉它谁会疼？
- **所处阶段**：原型验证 / 迭代开发 / 稳定维护 / 准备下线。
- **规模预期**：一次性 / 小团队 / 长期多人协作。
- **既有约定**：技术栈、目录结构、命名、发布方式。

阶段与规模直接决定工程强度：一次性脚本不该套分层架构，长期多人项目不能省测试。

### 3. 约束层：不能碰的红线

- 技术栈与依赖限制（不擅自引入新库）。
- 兼容性（旧数据、旧接口、旧客户端）。
- 安全与合规（鉴权、隐私、审计）。
- 不可逆操作（数据迁移、删除、发布）。
- 时间与范围（哪些明确不做）。

### 4. 验收层：怎么算做完

- **命令级**：跑哪个测试 / 哪条命令、看到什么输出。
- **行为级**：用户能做什么之前做不到的事。
- **边界级**：异常输入、空态、失败路径怎么表现。

写不出验收判据，说明意图还没识别清楚。

## 输出模板

```markdown
【意图识别】
- 真实目标：<一句话，可验收>
- 项目定位：<服务对象 / 核心问题 / 阶段 / 规模>
- 干系人：<谁关心结果，谁会被影响>
- 硬约束：<技术栈 / 兼容 / 安全 / 不可逆>
- 未知与假设：<逐条，标注为假设并给出默认值>
- 验收定义：<命令或可观察行为>
- 不做什么：<明确排除项>
```

## 规则

- **假设显式化**：缺信息按最合理默认值补全并标注「假设」，不阻塞、不反复追问。
- **不替换目标**：只提高精度，不擅自扩大或缩小范围。
- **方向分歧**：按 AGENTS.md「五方案对比 → 自选最优 → 直接执行」处理，不把选择抛回用户。
- **冲突即指出**：用户要求与项目定位矛盾时，直接说明并给替代方案。
- **可证伪**：验收定义必须能被一条命令或一次观察否证。

## 与后续步骤的衔接

意图识别 → `skill-router` 选技能 → `task-slicing` 拆片 → 开工 → 每片验证 → `delivery-quality-bar` 收口。

项目定位不明且仓库陌生时，接 `repo-cartography` 先出一页地图；规模与阶段判断影响架构强度时，接 `senior-architect`。

## 反模式

- 把用户的方案当需求（他要的是「别再卡」，不是「上 Redis」）。
- 用「我理解你要…」替代确认，然后按自己的理解做完全程。
- 识别完不写下来，做到一半忘了原始目标。
- 对小脚本套用大项目流程，或对大项目省略验收标准。
